## 0. 가장 중요한 실행 원칙

이 문서는 단순한 의견서가 아니라 **실제 코드 변경을 수행하기 위한 작업 명세서**다.

다음 원칙을 반드시 지켜라.

1. 아래 버그 목록을 사실로 단정하지 말고 **현재 `mmorpg_online` 브랜치에서 먼저 재검증**한다.
2. 재현되거나 코드 경로상 명백히 입증된 문제만 수정 완료로 표시한다.
3. 미재현 항목은 임의로 고치지 말고, 조사 결과와 미재현 이유를 기록한다.
4. 파일명·함수명·경로가 달라졌다면 `rg`, 심볼 검색, 호출 관계 추적으로 실제 위치를 찾는다.
5. 신규 기능 추가보다 **데이터 무결성, UI 안정성, 입력 안정성, 회귀 테스트**를 우선한다.
6. 여러 문제를 하나의 거대한 리팩터링으로 처리하지 않는다. 원인별로 작고 검증 가능한 변경을 만든다.
7. 기존 게임 플레이와 저장 데이터의 하위 호환성을 최대한 보존한다.
8. 보안 문제는 UI에서 숨기는 방식으로 해결하지 않는다. 권한 검증은 서버 또는 Firebase Rules에서 수행한다.
9. 테스트를 통과시키기 위해 테스트를 약화하거나 삭제하지 않는다. 잘못된 테스트라면 이유를 문서화하고 동작 기반 테스트로 교체한다.
10. 실제 배포, 프로덕션 Firebase Rules 적용, 운영 데이터 마이그레이션은 수행하지 않는다. 로컬·에뮬레이터 기준으로 안전성을 검증하고 배포 절차를 문서화한다.
11. 확인하지 않은 내용을 “수정 완료”라고 보고하지 않는다.
12. 작업 도중 발견한 추가 버그도 동일한 형식으로 등록하고, 심각도와 재현 절차를 명시한다.

## 4. 심각도 기준

### P0 — 서비스 차단

데이터 변조, 계정 간 오염, 임의 보상, 운영자 권한 탈취, 캐시 파괴처럼 서비스 신뢰를 무너뜨리는 문제다.

### P1 — 핵심 플레이 장애

일반적인 플레이에서 자주 발생하고, 조작·저장·복원·화면 표시를 직접 방해하는 문제다.

### P2 — 중요 회귀 및 환경 의존 문제

특정 기기, 화면 회전, 멀티터치, 계정 전환, 네트워크 불안정 상황에서 발생하는 문제다.

### P3 — 성능·완성도

즉시 플레이를 막지는 않지만 프레임 안정성, 발열, 유지보수성을 악화시키는 문제다.

# 5. 우선순위별 작업 목록

## Phase 1. P0 보안·데이터 무결성

### SEC-01. Firebase Realtime Database 규칙 감사 및 deny-by-default 전환 준비

#### 조사

- 루트에 `.read: true`, `.write: true` 또는 사실상 동일한 전면 개방 규칙이 존재하는지 확인한다.
- 플레이어 프로필, 인벤토리, 재화, 경험치, 퀘스트, 몬스터, 파티, 채팅, PvP 데이터 경로를 목록화한다.
- 각 경로의 읽기·쓰기 주체를 표로 정리한다.
- 클라이언트가 자신의 UID 외 데이터를 쓸 수 있는지 Firebase Emulator로 검증한다.

#### 구현

가능한 범위에서 다음 원칙을 적용한다.

- 루트는 기본 거부
- 인증되지 않은 사용자의 민감 데이터 읽기·쓰기 차단
- 사용자 자신의 비민감 프로필만 제한적으로 쓰기 허용
- 재화, 경험치, 인벤토리, 보상 결과의 클라이언트 직접 쓰기 차단
- 데이터 타입, 범위, 필수 필드 validation 추가
- 파티·친구·채팅은 참여자·수신자 권한 검증
- 운영자 기능은 Custom Claims 또는 서버 검증 사용

#### 안전 조건

프로덕션에 즉시 배포하지 않는다. 현재 클라이언트가 전면 개방 규칙에 의존한다면 다음을 수행한다.

1. Emulator 전용 강화 규칙 작성
2. 차단되는 기존 쓰기 목록 작성
3. 필요한 서버 함수 또는 트랜잭션 API 설계
4. 단계별 배포·마이그레이션 절차 작성

규칙만 강화해 게임을 전부 깨뜨리는 변경은 완료로 간주하지 않는다.

#### 테스트

- 비로그인 전체 쓰기 거부
- 사용자 A가 사용자 B의 프로필 수정 불가
- 사용자가 자신의 골드·경험치 임의 증가 불가
- 스키마 범위를 벗어난 값 거부
- 정상 채팅 또는 허용 프로필 수정은 성공

### SEC-02. 클라이언트 하드코딩 운영자·개발자 암호 제거

#### 조사

다음 패턴을 검색한다.

```bash
rg -n "password|developer|admin|devmode|운영자|개발자|비밀번호" src index.html .
```

클라이언트 번들에 비밀번호 또는 운영자 판정 로직이 포함되어 있는지 확인한다.

#### 구현

- 클라이언트 문자열 비교 방식 제거
- 로그인 사용자의 서버 측 claim 또는 명시적 권한 응답으로 운영 UI 표시
- 실제 운영 명령은 서버에서 권한을 다시 검증
- 운영 명령 감사 로그 설계 또는 구현
- 운영자 UI를 숨기는 것만으로 보안 완료 처리하지 않음

서버 인프라가 없다면 취약 기능을 기본 비활성화하고, 안전한 서버 권한 구조를 `SECURITY_AND_SERVER_AUTHORITY_PLAN.md`에 구체적으로 제시한다.

### NET-01. 클라이언트 권한 전투·보상 구조 감사

#### 조사

다음 값이 어디에서 계산되고 저장되는지 추적한다.

- 데미지
- 치명타
- 몬스터 사망
- 경험치
- 골드
- 드롭
- 인벤토리 증감
- 퀘스트 완료 보상
- PvP 승패
- 거래·우편 첨부물

클라이언트가 최종 결과를 직접 데이터베이스에 기록한다면 P0로 분류한다.

#### 구현 원칙

- 이동 표현은 클라이언트 예측을 유지할 수 있음
- 전투 결과와 경제 결과는 서버 또는 신뢰 가능한 호스트 검증 필요
- 동일 몬스터 사망 보상은 정확히 한 번만 지급
- 중복 패킷·재접속·지연으로 보상이 반복되지 않도록 idempotency key 사용
- 서버 구현이 불가능한 범위는 임시 검증 계층과 명시적 후속 계획을 남김

#### 금지

- 클라이언트 난독화로 치팅 방지 완료 처리
- UI 버튼 비활성화로 권한 검증 대체
- 로컬 값 범위 체크만으로 서버 권한이라고 주장

## Phase 2. P1 UI 설정 및 핵심 UX

### UI-01. 고정 조이스틱 위치 저장값이 실제 플레이에서 무시되는 문제

#### 확인할 가능성 높은 원인

- UI 편집 모드에서만 저장 위치가 적용됨
- 편집 종료 시 `TouchHandler`에 고정 좌표 대신 `null` 또는 동적 모드가 전달됨
- UIManager와 TouchHandler가 같은 DOM 요소의 위치를 서로 덮어씀

#### 목표 동작

UI 설정에 다음 상태가 명확히 존재해야 한다.

```text
joystick.mode = dynamic | fixed
joystick.position = normalized x/y
joystick.scale
```

- `dynamic`: 터치 시작 위치를 기준으로 생성
- `fixed`: 사용자가 저장한 위치를 계속 사용
- 편집 모드 여부와 조이스틱 동작 모드는 서로 독립
- 기존 사용자 데이터는 기본적으로 `dynamic`으로 안전 마이그레이션

#### 합격 기준

1. 고정 모드에서 위치 변경
2. 저장
3. 설정창 닫기
4. 플레이
5. 새로고침
6. 재로그인
7. 화면 회전 후 원래 방향 복귀

위 모든 단계에서 저장 위치가 유지되어야 한다.

### UI-02. 카메라 시야 슬라이더 조작 중 전체 캔버스 반복 리사이즈

#### 구현 원칙

- `input` 이벤트에서는 카메라 줌만 미리보기
- 한 프레임에 한 번만 적용하도록 `requestAnimationFrame` 또는 동등한 방식 사용
- 영구 저장은 `change`, `pointerup`, `touchend` 등 조작 종료 시점에 수행
- 캔버스 backing resolution은 viewport 또는 DPR이 실제로 변경된 경우에만 갱신
- 이전 설정과 동일하면 저장·리사이즈 생략

#### 계측

테스트에서 슬라이더 드래그 중 다음을 측정한다.

- `game.resize()` 호출 수
- canvas `width`/`height` 변경 횟수
- 설정 저장 횟수

#### 합격 기준

슬라이더를 여러 단계 드래그해도 canvas backing size가 반복 변경되지 않아야 하며, 최종 값만 저장되어야 한다.

### UI-03. UI 배치와 게임 캔버스가 서로 다른 viewport 기준을 사용

#### 목표 구조

`ViewportMetrics` 또는 동등한 단일 모듈을 도입하고 다음 값을 한 곳에서 제공한다.

```text
viewportWidth
viewportHeight
viewportOffsetTop
viewportOffsetLeft
safeAreaTop
safeAreaRight
safeAreaBottom
safeAreaLeft
devicePixelRatio
gameViewportRect
orientation
inputModality
```

#### 원칙

- UI 좌표는 `window.innerWidth/innerHeight`가 아니라 실제 게임 컨테이너 기준
- 모바일 주소창, 키보드, PWA standalone, 분할 화면, 노치 안전 영역 고려
- 저장 좌표는 가능하면 정규화된 값 사용
- 렌더링 좌표와 입력 좌표가 같은 기준계를 사용
- `visualViewport`가 없는 환경에는 명확한 fallback 제공

#### 합격 기준

- 세로 → 가로 → 세로 후 원래 위치 복구
- 주소창 접힘/펼침 후 UI가 안전 영역 밖으로 나가지 않음
- 소프트 키보드가 열렸다 닫혀도 전투 HUD가 영구 이동하지 않음
- PWA와 브라우저 실행 결과가 일관됨

### UI-04. 같은 브라우저에서 계정 간 UI 레이아웃 오염

#### 목표 저장 구조

실제 인증 UID를 기준으로 로컬 저장을 분리한다.

```text
yurika_ui_layout_v2:{uid}
```

정확한 키 이름은 기존 규칙과 충돌하지 않도록 결정하되, 반드시 사용자별이어야 한다.

#### 필수 상태 분리

```text
serverLayout
localPersistedLayout
editingDraft
activeResolvedLayout
```

#### 마이그레이션

- 기존 전역 키가 있다면 UID 확인 후 한 번만 사용자 키로 이동
- 로그인 전에는 사용자 레이아웃을 서버에 저장하지 않음
- 로그아웃 시 메모리 draft와 active layout의 사용자 종속 상태 제거
- 계정 변경 시 새 UID의 레이아웃을 다시 로드
- A 계정의 로컬 timestamp가 B 계정 서버값을 덮지 못하게 함

#### 테스트

1. A 계정에서 UI 배치 저장
2. 로그아웃
3. B 계정 로그인
4. B의 레이아웃이 A와 다름을 확인
5. B 저장
6. 다시 A 로그인
7. A 레이아웃이 유지됨을 확인

### UI-05. 원격 저장 실패에도 저장 완료로 표시되는 문제

```text

editing
saved-local
syncing
synced
sync-failed
```

- 서버 저장 Promise를 추적
- 성공 전 “서버 저장 완료” 메시지 금지

- 오프라인이면 “로컬 저장됨 / 서버 동기화 대기” 표시
- 중복 저장 요청은 최신 요청 기준으로 정리
- 창 종료 전에 미동기화 상태를 알 수 있어야 함

#### 합격 기준

네트워크를 차단한 상태에서 저장하면 성공으로 위장하지 않고, 온라인 복귀 후 재시도 또는 자동 동기화가 명확하게 이루어져야 한다.

### INPUT-01. `Shift+S` 해제 순서에 따라 액션 상태가 남는 문제

- Shift 누름 → S 누름 → S 해제 → Shift 해제
- S 누른 상태에서 창 포커스 상실
- 단축키 반복 입력

모든 경우 active action set이 비어야 한다.

### PWA-01. 오프라인 버전 확인 실패를 새 버전으로 오인하여 캐시 삭제·재시작

#### 조사

- 서비스 워커 버전 API가 실패 시 어떤 status와 body를 반환하는지 확인
- 클라이언트가 `response.ok`를 검사하는지 확인
- 응답 body가 버전 형식인지 검증하는지 확인
- 포커스 복귀·온라인 복귀 시 업데이트 검사가 반복되는지 확인

#### 구현 원칙

- 네트워크 실패는 “업데이트 존재”가 아니라 “확인 불가”
- 실패 응답은 503 등 명확한 오류 상태 또는 reject
- 클라이언트는 `response.ok`와 버전 형식을 모두 검증
- 버전 불명 상태에서는 캐시 삭제 금지
- 새 리소스 다운로드와 검증이 끝난 후에만 캐시 전환
- 서비스 워커 등록 해제와 전체 캐시 삭제를 기본 복구 방식으로 사용하지 않음
- 자동 새로고침 루프 방지용 guard 필요

#### 테스트

- 완전 오프라인에서 PWA 시작
- 네트워크가 불안정한 상태에서 포커스 복귀
- 버전 endpoint가 500 반환
- 버전 body가 `error`, 빈 문자열, HTML 반환
- 정상 새 버전 존재

오류 상황에서 기존 캐시가 유지되고 게임이 반복 재시작되지 않아야 한다.

### UI-07. UI 배치 초기화가 즉시 영구 저장되는 문제

### UI-10. 화면 회전 한 번에 다수 리사이즈 타이머가 중복 실행되는 문제

#### 목표 구조

화면 크기 변경 책임을 하나의 모듈로 통합한다.

- `ResizeObserver`
- `visualViewport.resize`
- 필요한 경우 `orientationchange`
- `requestAnimationFrame` 기반 병합
- 같은 크기에는 no-op
- 연속 프레임에서 크기가 안정된 뒤 최종 적용

#### 금지

80ms, 120ms, 180ms, 360ms 등 서로 다른 임의 타이머를 여러 시스템이 독립적으로 추가하지 않는다.

#### 계측

한 번 회전했을 때 다음 호출 수를 기록한다.

- viewport recompute
- game resize
- layout apply
- canvas backing resize

가능하면 각 1회 또는 안정화를 위한 최소 횟수로 제한한다.

### UI-11. UI 편집기가 다른 시스템의 인라인 스타일을 제거하는 문제

```text

display
transform
width
height
left
right
top
bottom
```

UI 편집기가 소유한 속성만 해제한다.

# 6. UI 설정 시스템 권장 아키텍처

아래 구조를 그대로 복제할 필요는 없지만, 동일한 책임 분리를 달성해야 한다.

## 6.1 단일 진실 원본

```text
Server Profile
    ↓ load/sync
UiLayoutRepository
    ↓ normalized model
UiLayoutStore
    ├─ persistedLayout
    ├─ editingDraft
    └─ activeResolvedLayout
    ↓ render
UiLayoutRenderer
    ↓ CSS variables / wrappers
DOM
```

`TouchHandler`는 입력과 조이스틱 동작을 담당하지만, 사용자 레이아웃 저장소를 직접 소유하지 않는다.

## 6.2 권장 데이터 모델

```json
{
  "schemaVersion": 2,
  "revision": 17,
  "updatedAtServer": 0,
  "deviceId": "generated-device-id",
  "profiles": {
    "desktop": {},
    "portrait": {},
    "landscape": {}
  },
  "joystick": {
    "mode": "dynamic",
    "position": { "x": 0.15, "y": 0.78 },
    "scale": 1
  },
  "camera": {
    "zoom": 1
  }
}
```

실제 필드명은 기존 데이터와 맞추되 다음 조건을 지킨다.

- schema version 존재
- 사용자별 저장
- 방향별 프로필 분리
- revision 존재
- 정규화 좌표
- 명시적 조이스틱 모드

## 6.3 마이그레이션 요구사항

- 구버전 데이터가 없으면 기본값 생성
- 구버전 전역 로컬 키는 로그인한 UID에만 1회 귀속
- 마이그레이션 완료 flag 또는 schema version 기록
- 실패해도 원본 구버전 값을 즉시 삭제하지 않음
- 파싱 실패 시 안전한 기본값 사용하고 오류 로그 남김
- 잘못된 좌표, NaN, 범위 초과 scale을 정규화

## 6.4 저장 경쟁 조건

- 편집 중 서버에서 새로운 버전이 도착해도 draft를 갑자기 덮지 않음
- 저장 중 연속 클릭은 중복 write를 만들지 않음
- 느린 이전 요청이 빠른 최신 요청을 덮지 않게 함
- 마지막 성공 revision을 추적
- 로그아웃 이후 완료된 Promise가 다음 계정 상태를 수정하지 않게 함

# 7. 자동화 테스트 요구사항

## 7.1 기존 검증 스크립트 감사

특히 `scripts/validate-ui-layout.js` 또는 유사 파일이 다음 방식인지 확인한다.

- 특정 문자열이 있으면 성공
- 특정 함수명이 등장하면 실패
- 실제 브라우저 동작을 검증하지 않음

잘못된 구조를 고착하는 검증이라면 이유를 문서화하고 동작 기반 테스트로 교체한다.

## 7.2 브라우저 테스트

프로젝트에 이미 브라우저 테스트 도구가 있으면 그것을 사용한다. 없다면 lockfile로 패키지 관리자를 확인한 후 Playwright 등 최소한의 E2E 인프라 도입을 검토한다.

필수 시나리오:

- UI 위치 저장·새로고침·재로그인
- 세로/가로 레이아웃 독립성
- 계정 A/B 레이아웃 분리
- 저장 실패 표시
- 카메라 슬라이더 드래그
- 방향 잠금 실패
- 대형 터치 태블릿 모드
- Shift+S 해제 순서
- 멀티터치 취소
- PWA 오프라인 시작과 버전 조회 실패
- 팝업 z-index 및 click-through

## 7.3 단위 테스트

가능하면 순수 로직을 DOM·Firebase에서 분리해 다음을 단위 테스트한다.

- layout migration
- layout conflict resolution
- viewport normalization
- physical key → resolved action map
- version response validation
- spawn point validation
- unique ID generation

## 7.4 Firebase Emulator 테스트

- 인증 없음
- 본인 UID
- 다른 UID
- 잘못된 타입
- 허용 범위 초과 값
- 재화 직접 증가
- 정상 프로필 수정

## 7.5 회귀 테스트 실패 정책

기존 테스트가 잘못된 구현을 강제한다면 다음 순서로 처리한다.

1. 기존 테스트가 왜 잘못되었는지 증명
2. 사용자 관점 기대 동작 작성
3. 새 동작 테스트 추가
4. 기존 정적 테스트 수정 또는 제거
5. 변경 사유 문서화

테스트를 단순히 삭제하고 넘어가지 않는다.

## 10.1 반드시 평가할 항목

### 핵심 플레이 루프

- 플레이어가 1분, 10분, 30분 단위로 반복하는 행동
- 사냥 외 의미 있는 선택이 있는지
- 자동전투가 최적 전략이 되는 구조인지

### 퀘스트 다양성

- 처치·이동·보스 퀘스트 비율
- 동일 행동을 숫자만 바꿔 반복하는지
- 환경, NPC, 협동, 퍼즐, 선택지 사용 여부

### 월드 밀도

- 맵 크기 대비 스폰, NPC, 오브젝트, 사건의 밀도
- 이동 시간이 탐험인지 공백인지
- 지역마다 규칙과 상호작용이 달라지는지

### 적과 전투 다양성

- 일반 몬스터 종류 수
- 역할 구분: 근접, 원거리, 방어, 제어, 지원, 이동 강제
- 스킬 선택과 위치 결정을 실제로 요구하는지
- 보스가 단순 체력 증가인지 패턴 학습인지

### 서사 통합

- 기획 문서의 핵심 서사가 첫 5분에 드러나는지
- 프롤로그와 장기 서사의 연결
- 퀘스트 행동이 인물 관계와 세계관을 전달하는지

### MMO 필요성

- 다른 플레이어가 단순 DPS 증가 외 역할을 갖는지
- 협동 기믹, 공동 목표, 사회적 상호 의존이 있는지
- 파티·친구·채팅 기능이 실제 콘텐츠에 의해 요구되는지

### UI 정보 우선순위

- 항상 노출되는 버튼 수
- 전투 중 필요한 정보와 비전투 기능의 분리
- 모바일에서 월드보다 HUD가 더 지배적인지
- UI 편집이 취향 기능인지 오류 복구 기능인지

### 콘텐츠 지속성

- 현재 레벨·지역·퀘스트 분량
- 엔드게임 루프
- 지역 추가 없이도 반복 변주 가능한 시스템
- 장기 성장과 빌드 선택

### 독자 IP 및 상용화 위험

- 기존 유명 IP를 연상시키는 이름·에셋·캐릭터 존재 여부
- 임시 데이터와 실제 상용 데이터를 구분
- 법률 판단을 단정하지 말고 브랜드·운영 리스크로 설명

- 데이터상 명백한 오탈자·중복·불가능 조건은 수정 가능
- 밸런스 수치의 대규모 변경은 보고서와 별도 제안으로 남김

# 12. 코드 품질 규칙

- 함수가 너무 많은 책임을 갖고 있다면 작은 모듈로 분리하되, 관련 없는 대규모 재작성은 피한다.
- 전역 상태 추가를 피한다.
- DOM 요소와 저장 모델을 직접 강결합하지 않는다.
- Promise rejection을 삼키지 않는다.
- `catch {}`로 사용자·로그 모두에게 오류를 숨기지 않는다.
- timeout 기반 보정은 마지막 수단으로만 사용한다.
- magic number에는 이유를 주석 또는 상수명으로 표현한다.
- 저장 데이터 파싱에는 방어 코드가 있어야 한다.
- null DOM 요소에 대한 안전 처리를 한다.
- 로그에는 UID, 토큰, 비밀번호 등 민감 정보를 남기지 않는다.
- 새 라이브러리는 반드시 필요할 때만 추가한다.
- lockfile과 package manager를 일치시킨다.
- 기존 코딩 스타일을 존중한다.

# 16. 즉시 시작 지시

이 문서를 읽은 뒤 질문으로 작업을 지연하지 말고 다음을 즉시 수행하라.

1. 저장소 상태와 브랜치를 확인한다.
2. `package.json`, README, 핵심 파일을 읽는다.
3. UI 설정의 로드 → 편집 → 저장 → 서버 동기화 → 적용 흐름을 추적한다.
4. P0/P1 항목을 실제 코드와 테스트로 재검증한다.
5. `reports/BUG_AUDIT_AND_REPRODUCTION.md`를 먼저 생성한다.
6. 재현 테스트를 추가한다.
7. 작은 변경 단위로 수정한다.
8. 각 변경 후 테스트한다.
9. 디자인 분석 보고서와 최종 구현 결과를 작성한다.

불확실한 부분은 임의로 단정하지 말고, 코드 근거와 테스트 결과를 통해 결론을 내려라.
