# 싱글 기준선 이후 최적화 방향

## 범위

- 2026-04-08 싱글 플레이 측정 결과를 현재 브랜치의 새로운 기준선으로 기록한다.
- 현재 브랜치에서는 싱글의 체감 품질을 유지하면서, 이후 최적화 초점을 멀티플레이 RTDB hot path로 옮긴다.
- 구조 전면 재설계나 RTDB 외 실시간 전송 전환은 현재 브랜치 범위에서 제외한다.

## 현재 기준선

- 테스트 조건
  - 슬라임 필드
  - 1클라이언트
  - 2026-04-08 08:30 ~ 09:20
  - 매직 미사일, 파이어볼, 체인 라이트닝을 지속 사용하며 50분간 사냥
- 측정 결과
  - 다운로드: 8.63MB / 50분
  - 시간당 환산: 약 10.36MB / 시간
  - RTDB 로드: 1% 미만
  - 규칙 평가: 약 7.4천

## 해석

1. 싱글 기준으로는 현재 상태가 이전보다 충분히 만족스러운 편이다.
2. 현재 브랜치의 최적화 초점은 더 이상 싱글 미세조정보다 멀티플레이 fan-out 비용과 authoritative 보상 흐름 정리에 둔다.
3. 싱글은 이제 "추가 개선 대상"보다 "회귀 감시 대상"으로 다루는 것이 맞다.

## 현재 병목 가설

### 1. 일반 사냥 보상 루프가 가장 비싼 후보

- 일반 몬스터 처치 시 골드/경험치/HP를 drop 경로로 생성하고, 다시 수거 요청과 보상 지급을 거친다.
- 멀티에서는 이 구조가 반복될수록 RTDB write / read / fan-out이 커진다.
- 관련 파일
  - `src/js/world/MonsterManager.js`
  - `src/js/core/NetworkManager.js`
  - `src/js/entities/Player.js`

### 2. 전투 중 몬스터 상태 전달 주기가 아직 촘촘한 편

- 활성 몬스터와 근접 몬스터의 위치/상태 전달이 누적 비용으로 작동할 가능성이 높다.
- 특히 2클라, 3클라 자동사냥 측정에서 분당 스파이크가 계속 유지된 점과 맞물린다.
- 관련 파일
  - `src/js/world/MonsterManager.js`
  - `src/js/core/NetworkManager.js`

### 3. 프로필 저장은 여전히 무거운 편

- `saveState()`가 전체 프로필 저장에 가깝고, 경험치/골드/퀘스트/회복이 겹치면 저장 빈도가 올라간다.
- 싱글에서는 이미 상당히 나아졌지만, 멀티 자동사냥 구간에서는 여전히 누적 비용 후보로 남는다.
- 관련 파일
  - `src/js/entities/Player.js`
  - `src/js/core/NetworkManager.js`

## 다음 최적화 우선순위

### P0-1. 일반 몬스터 보상 hot path 축소

- 목표
  - 일반 사냥의 골드/경험치/HP 보상에서 RTDB drop 루프를 최대한 줄인다.
- 방향
  - 일반 몬스터의 골드/경험치/HP는 host authoritative reward bundle로 직접 지급한다.
  - 실제 바닥 드롭은 아이템류 위주로 한정한다.
  - 드롭 애니메이션이 꼭 필요하면 로컬 연출만 남기고 authoritative 보상은 별도 번들로 처리한다.
- 기대 효과
  - 멀티 자동사냥 시 가장 큰 반복 비용 절감 가능성이 높다.
- 영향 파일
  - `src/js/world/MonsterManager.js`
  - `src/js/core/NetworkManager.js`
  - `src/js/entities/Player.js`

### P0-2. 몬스터 전투 sync 주기 완화

- 목표
  - 전투 중에도 체감 품질을 해치지 않는 범위에서 몬스터 상태 전송 빈도를 낮춘다.
- 방향
  - 보스, 돌진, 캐스팅, 사망 직전/직후 같은 핵심 상태만 빠른 주기를 유지한다.
  - 일반 슬라임의 평상시 이동/추적은 더 느린 주기로 보낸다.
  - 셀 이동이 없는 정적 구간에서는 delta가 거의 없으면 skip한다.
- 영향 파일
  - `src/js/world/MonsterManager.js`
  - `src/js/core/NetworkManager.js`

### P0-3. `saveState()`를 patch형 저장으로 더 분리

- 목표
  - 자동사냥 중 반복 저장의 payload와 빈도를 더 줄인다.
- 방향
  - 경험치/골드/HP/퀘스트 킬 카운트는 경량 patch 저장으로 우선 처리한다.
  - 인벤토리/장비/대형 프로필은 실제 변경 시에만 full save를 유지한다.
  - 일정 시간 내 연속 보상은 debounce / coalesce한다.
- 영향 파일
  - `src/js/entities/Player.js`
  - `src/js/core/NetworkManager.js`

### P1. 플레이어 전달 비용 절감은 안정화 이후 진행

- 목표
  - 3클라 이상에서 플레이어 가시성/이름/late join이 안정화된 뒤 player hot path fan-out도 줄인다.
- 방향
  - 현재 visibility 안정화가 먼저다.
  - 그 다음 단계에서 플레이어도 셀 기반 snapshot 전달로 옮긴다.
- 영향 파일
  - `src/js/core/NetworkManager.js`
  - `src/js/entities/RemotePlayer.js`
  - `src/js/world/scenes/WorldScene.js`

## 이번 단계에서 일부러 미루는 것

- 싱글만을 위한 추가 미세 최적화
- RTDB 밖 별도 realtime 채널 도입
- 멀티플레이 제거 또는 구조 전면 재설계
- 실사용자 버그와 직접 연결되지 않은 대규모 리팩터링

## 검증 기준

### 싱글 기준선 유지

- 슬라임 필드 50분 사냥 기준 대략 12MB / 시간 이내 유지
- 체감 회귀가 없어야 한다.

### 멀티 단기 목표

- 2클라 자동사냥 총 다운로드를 현재 대비 의미 있게 절감
- 3클라 자동사냥 총 다운로드를 현재 대비 의미 있게 절감
- 호스트/게스트 전투 결과, 가시성, 보상, 퀘스트 카운트가 깨지지 않아야 한다.

## 트레이드오프

- 일반 보상 루프를 줄이면 연출과 authoritative 처리 분리가 필요해 구현 난도가 오른다.
- 몬스터 sync 주기를 늦추면 체감 움직임이 둔해질 수 있어, 보스/특수 패턴은 예외 처리가 필요하다.
- 저장을 patch형으로 쪼개면 코드 경로가 늘지만, 현재 브랜치에서 얻는 비용 절감 효과가 크다.

## 결론

- 싱글은 현재 기준으로 "만족스러운 수준"에 들어왔다.
- 이후 최적화의 중심은 멀티 자동사냥 RTDB 비용 절감으로 옮긴다.
- 다음 실제 작업은 `일반 몬스터 보상 hot path 축소 -> 몬스터 sync 주기 완화 -> saveState patch 분리` 순서가 가장 효과적이다.
