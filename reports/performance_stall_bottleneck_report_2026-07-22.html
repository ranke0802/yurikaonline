1. 요약 결론

P0 / 로그인 프리즈

월드 진입 중 보상 백로그를 전부 기다림

WorldScene.enter()가 보상 컨슈머 등록을 await하고, 컨슈머 등록 함수가 즉시 모든 보상 백로그를 읽고 펌프한다. 각 보상 receipt는 플레이어에게 적용된 뒤 전체 프로필 즉시 저장으로 이어진다. 고레벨 계정은 프로필 크기가 커서 건당 저장 비용이 크고, 백로그 개수만큼 반복된다.

P0 / 플레이 중 4~5초 정지

idle 위치 저장이 전체 프로필 즉시 저장

플레이어가 이동 후 3초간 멈추면 위치 저장 목적으로 saveState(false, { debounceMs: 0 })가 호출된다. 그러나 실제로는 위치만 저장하지 않고 inventory, questState, pending rewards 등 전체 프로필을 저장한다.

P0 / 공통 병목

작은 patch도 전체 체크포인트로 변환

savePlayerDataPatch()는 debounce 여부와 무관하게 먼저 localStorage 체크포인트를 갱신한다. 이 과정에서 기존 full profile을 읽고, patch와 merge하고, 전체 profile을 sanitize/stringify/setItem 한다.

4. 왜 고레벨 계정에서 더 심한가

이 프로젝트의 저장 비용은 단순히 레벨 숫자 자체보다 프로필 객체 크기에 비례한다. 고레벨 계정은 일반적으로 장비 옵션, 인벤토리, 퀘스트 진행 상태, 보상 수령 ID, pending reward, cooldown, map position 등이 더 크다. 그런데 현재 저장 경로는 작은 변경도 전체 프로필을 여러 번 순회한다.

6. 우선 수정안

P0 월드 진입에서 보상 백로그 drain을 await하지 않기

  • WorldScene.enter()는 첫 렌더/입력 가능 상태를 먼저 완료해야 한다.
  • setNormalRewardConsumer(), setDurableRewardConsumer()는 컨슈머만 등록하고 즉시 반환하도록 분리한다.
  • 백로그는 첫 프레임 이후 requestAnimationFrame 또는 time budget 기반으로 처리한다. 예: 프레임당 1건 또는 8ms budget.
  • 백로그 처리 중에는 “미수령 보상 동기화 중” 같은 비차단 UI를 보여준다.

  5. 전투 중 피격 후 4.2~5.2초 뒤 damage_hp_patch flush와 long task가 겹치는지 확인한다.

9. 최종 판단

1순위 원인: 프로필 저장 시스템이 고레벨 대형 프로필에 대해 너무 무겁고, 그 무거운 작업이 로그인/보상/idle 위치 저장/피격 저장 같은 사용자 체감 hot path에서 실행된다.

로그인 30초 프리즈: 월드 진입 전에 보상 백로그 전체를 처리하고, 보상마다 전체 즉시 저장을 수행하는 경로가 가장 유력하다.

플레이 중 4~5초 프리즈: idle 위치 저장의 full save, HP/reward debounce flush, patch 저장 전 full checkpoint merge/write가 가장 유력하다.

해결 방향: 첫 렌더/입력 가능 시점에서 저장과 보상 백로그를 분리하고, hot path의 저장을 field-level patch + throttled async checkpoint로 축소해야 한다.
