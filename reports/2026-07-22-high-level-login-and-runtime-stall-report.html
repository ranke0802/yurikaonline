맵/몬스터/드랍 확장 이후

프로필에 쌓이는 아이템, pending reward, claimed reward, boss scroll, option reroll stone, 강화석 데이터가 늘어났다. “맵 확장” 자체보다 “확장 후 프로필 payload가 커진 상태에서 저장 안정화 로직이 전체 payload를 반복 처리”하는 조합이 문제다.

우선순위별 개선 방향

  1. 전체 프로필 저장을 즉시 중단하고, hot-path는 필드 patch 전용으로 분리.
    idle 위치 저장, hp/mp, currentZoneId, mapPositions는 root transaction 전체 병합이 아니라 users/$uid/profile/x, .../mapPositions/$zoneId 같은 얕은 multi-location update로 처리해야 한다.
  2. local checkpoint를 full profile이 아니라 compact critical checkpoint로 축소.
    최소 필드: level, exp, stats, skillLevels, manastone, equipment, inventory 핵심, questState 요약, currentZoneId, mapPositions. pending reward/outbox 전체는 별도 journal로 분리한다.
  3. sanitize는 저장마다 전체 재귀 수행하지 말고 dirty field 단위로 캐시.
    이미 안전한 schema를 쓰는 내부 객체는 재정렬 sanitize를 생략하거나, 개발/마이그레이션/복구 때만 수행한다.
  4. 로그인 복구 후보 조회를 조건부로 축소.
    root profile이 명백히 정상이고 최신이면 recovery/profileBackups/local anonymous checkpoint를 즉시 읽지 않는다. “초기화 의심”일 때만 deep recovery를 수행한다.
  5. 백업 저장 reason 정책을 바로잡아 throttle 우회를 막는다.
    player_save, idle_profile_snapshot, reward_patch 같은 일반 reason이 매번 backup/prune을 통과하지 않게 해야 한다. 실시간 플레이 hot-path에서는 백업을 쓰지 않고, 레벨업/장비 획득/중요 재화 변화/종료 저장처럼 durable event에만 제한적으로 백업한다.
  6. telemetry payload byte 측정은 full stringify를 피한다.
    full profile payload는 샘플링하거나 key count/대략 크기만 기록하고, 저장 직전에 대형 객체를 통계용으로 다시 문자열화하지 않는다.
  7. 인벤토리 DOM은 가상화 또는 diff 업데이트.
    300칸 전체 재생성 대신 변경된 slot만 업데이트한다. 열린 detail modal도 선택 아이템 변경 시에만 갱신한다.
  8. outbox restore를 프레임 단위로 chunk 처리.
    reconnect 순간 512개를 한 번에 parse/validate/write하지 말고, 16~32개 단위로 requestIdleCallback 또는 frame budget queue로 나눈다.
  9. 측정용 performance mark를 hot path에 넣는다.
    profileBytes, checkpointStringifyMs, sanitizeMs, localStorageSetMs, transactionMs, inventoryDomMs를 dev overlay에 표시한다.
