# Hosting 다운로드 사고 분석과 재발 방지 — 2026-10-09

분석 기준: `mmorpg_online`, `b2a9ec2b59e1c5f96ee8347e41f76ae0235c1d59`
(v0.02.183). 이 문서의 개선은 로컬 작업이며, 푸시·Firebase 배포·운영 다운로드·
운영 데이터 또는 요금제 변경을 수행했다는 의미가 아니다.

## 확인된 원인

기존 merge workflow는 배포가 끝난 뒤 운영 Hosting에서 게임 회귀 검증을 다시
실행했다. `?local=1`은 계정 데이터를 로컬로 분리할 뿐, Hosting에서 받는 게임
파일을 로컬 파일로 바꾸지 않는다. 따라서 테스트의 이미지·코드 응답은 운영
다운로드였다. 이 구분을 놓친 검증 설계가 불필요한 운영 트래픽을 만들었다.

최신 구성을 정적으로 세면 배포 후 11개 단계, 18개 실행 명령, 47개 새 브라우저
context(게임 43, 구슬 fixture 3, 오디오 fixture 1), 게임 navigation/reload
100회였다. 테스트의 Playwright routing은 HTTP 캐시를 비활성화한다
(`node_modules/playwright-core/types/types.d.ts`의 route 설명).
해당 회귀 검사는 SW도 차단했으며 local mode는 원래 SW 자동 등록을 하지 않는다.
즉 일반 사용자에게 작동하는 이미지 캐시가 이 테스트에서는 작동하지 않았다.

별도의 기존 `verify-hosting-release.mjs`도 no-store로 자산 124개 응답
(고유 대상 121개, 62,474,682바이트)과 HTML/JS/manifest 등 81개 응답
(3,417,470바이트)을 받아 한 번에 **205요청 / 65,892,152 본문 바이트**를
사용했다. 62.47MB와 65.89MB 차이는 추가 코드/문서이며 압축 전후 차이가 아니다.
전체 검사 블록을 최대 6회 반복할 수 있었다. 실제 실패 위치에 따라 비용이
달라지므로 모든 실패가 6회 전량 다운로드였다고 간주하지 않는다.

다른 기기, 실제 바뀐 이미지 해시는 다시 다운로드될 수 있다.

API가 CacheStorage에 들어가지 않는 점도 통과했다.

## 적용한 방지책

- 운영 게임 브라우저 검증 11단계를 제거하고 기존 기능 검사는 배포 전 localhost에 유지.
- 모든 QA 네트워크 진입점에 실행 전 loopback URL 검사. Node fetch/http(s),
  리다이렉트, Playwright browser/API 트래픽도 제한. 브라우저에는 localhost
  거부 프록시를 강제하여 외부 하위 요청을 차단하면서 HTTP 캐시를 유지.
- `npm start`를 Firebase config 차단/CSP/로컬 모드 강제 서버로 교체.
- immutable 자산은 로컬에서 해시와 원본 바이트를 전수 검증.
  `release-manifest.json`은 커밋·버전·선택 파일 해시·전체 immutable 목록 digest를
  담는 작은 생성 파일이다. 비밀/사용자 데이터는 넣지 않는다.
- 배포 후 확인은 version/metadata/index/main/SW/AssetManifest/PWA manifest GET과
  immutable 이미지 HEAD 1회만 수행. 최대 **8요청 / 200,000 응답 본문 바이트**,
  이미지 GET·압축된 열린 스트림·리다이렉트·재시도 없음. 파일 크기가 예산을 넘으면
  실행 전에 실패. 첫 HTTP/크기/해시 오류에서 즉시 중단.
- 공개 헤더/메타데이터 확인으로 전체 CDN 파일 무결성까지 직접 증명한다고 주장하지
  않는다. 전체 자산 무결성은 배포 입력의 로컬 검사와 Hosting 배포 성공에 의존한다.
- CI 정책/원격 거절/바이트 예산/실제 WebP 서명/캐시 수명 검사를 자동화.
  상세 승인·배포 기준은 [AGENTS.md](../AGENTS.md)에 명시.

원격 checker는 기본적으로 localhost다. 원격 예외 플래그는 사용자 승인 그 자체가
아니며, 승인된 배포의 예산 안에서만 CI가 사용한다. CI 상한은 8요청/200,000본문바이트이며, CLI 정책과 클라이언트 자체의 절대
허용 상한은 8요청/524,288본문바이트(512KiB)다. CI 예산 증액은 새 승인이 필요하다.
동시에 제출한 여러 probe는 한 클라이언트 안에서 직렬화하고 누적 예산을 공유한다.
실패 이후 대기 중인 probe도 요청하지 않는다. **별도 프로세스/여러 workflow 실행
사이의 전역 월간 한도는 아니다.** 여러 승인 실행의 비용은 합산된다.

Content-Length 없음, chunked/길이 혼재, 로컬 파일과 다른 선언 길이, 잘린 본문,
압축 응답, 초과 크기, HTTP 실패/리다이렉트를 거절하는 로컬 음성 대조 검사를
통과했다. 실제 CLI도 버전 불일치 때 첫 요청 후 중단했다. 요청은 10초 제한,
16KiB 응답 헤더 제한, identity 인코딩과 Connection: close를 사용한다.

HTTP/TLS 헤더와 DNS/TCP 오버헤드는 본문 예산과 별도다. 거짓 Content-Length를
보내는 서버가 소켓이 닫히기 전에 추가 바이트를 밀어 넣는 경우, OS/네트워크
선행 수신까지 이 코드가 차단한다고 보장하지 않는다. 따라서 이것은 요청 수와
애플리케이션 응답 본문의 강제 한도이며 **과금 wire bytes의 절대 상한은 아니다**. quota/HTTP503 발생 시 재시도하거나 다른 도메인으로 우회하지 않는다.

## CI #572의 캐시 측정 경계 수정

`88df9b3`의 [CI #572](https://github.com/ranke0802/yurikaonline/actions/runs/38005337633)는
`witch:warm`에서 849,188바이트를 관측해 배포 전에 중단됐다. Hosting 배포와
운영 release 확인은 skipped였다. 당시 CI는 요청별 JSON을 업로드하지 않았으므로
그 실행의 정확한 이미지 경로/시각은 사후에 직접 확인할 수 없다.

크기가 정확히 일치하는 자산은 `/party-rpg-concept/assets/idle-witch.webp` →
`/assets/immutable/03be1a085990aefa1341e623.webp`이다. 로컬에서 최초 초상화의
DOM src 등록을 6초 늦춘 대조 조건을 넣자 기존 검사에서 같은 849,188바이트 실패가
재현됐다. cold 종료 관측 시 해당 캐시 키가 없었고, warm의 첫 GET 후 처음 저장됐다.
즉 기존 검사는 첫 화면의 이미지 로딩 완료를 보장하지 않은 채 warm으로 넘어갈 수
있었다. 이 재현은 CI 당시의 동일 스케줄을 입증하는 기록은 아니다.

수정 검사는 야영지와 원정 준비 화면의 실제 이미지 완료·decode·CacheStorage 응답을
확인한 뒤 화면을 넘긴다. 첫 필드의 진행 중 자산 로딩과 캐시 저장도 확인한다.
제품 SW와 런타임은 바꾸지 않았다. 모든 warm/update 이미지 본문 0바이트 조건은
그대로이며, 새로 시작된 이미지 요청을 필터링하지 않는다.

대조 검사는 두 가지다. 초상화 src 등록이 6초 늦어져도 cold 화면을 유지해
저장 완료 후 warm/update가 0바이트여야 한다. 반대로 cold에서 저장된 초상화를
CacheStorage/HTTP 캐시에서 제거하면 849,188바이트 재다운로드를 검출해 반드시
실패해야 한다. 대조 실행기는 이 의도된 실패의 경로·크기·이전 저장 여부까지 검증한다.

요청 시작/응답 finish/close 시각, 브라우저 요청 완료/취소, 화면 decode 및 캐시
관측 체크포인트를 JSON으로 기록한다. 캐시 관측 시각은 실제 cache.put의 내부 실행
시각과 구분한다. 실패하면 해당 JSON만 GitHub Actions artifact로 7일 보존한다.
이미지 본문, 요청 헤더, 쿠키, 인증 정보, 사용자 프로필은 업로드하지 않는다.

CI는 Chromium 153.0.8010.12, 이 클라우드의 설치 브라우저는 151.0.7922.173이다.
동일 버전 다운로드는 환경의 `403 Domain forbidden`으로 차단돼 우회하지 않았다.
로컬 대조 검증과 새 CI 결과를 구분해 보고한다. 진단과 재현 증거는
`/workspace/yurika-cache-ci-fix/`에 보관한다.

## 후속 CI의 궁수 생성 준비 경계 수정

`e19beba`의 [CI](https://github.com/ranke0802/yurikaonline/actions/runs/38007211442)는
Chromium 153에서 마법사·마녀·전사 warm/update 0바이트를 통과한 뒤 궁수 cold의
campReady에서 중단됐다. 배포와 운영 확인은 skipped였다. 보존된 artifact 분석상
화면 이미지 7개는 모두 완료·캐시 저장됐으며 실패한 이미지 요청도 없었다.
당시 snapshot에 busy/선택 작업/플레이어 직업이 없어 정확한 거짓 조건은 직접
확인할 수 없었다.

로컬에서 최초 prepareProfile 실행을 1초 늦추자 동일한 30초 timeout이 재현됐다.
`[data-camp=character]` 메뉴는 캐릭터 생성 전에도 비활성 상태로 존재한다.
기존 waitFor는 이 메뉴의 가시성만 확인해, busy=true/preparation 없음 상태에서
selectClass를 호출했다. 이 호출은 정상적인 제품 방어 조건에 의해 적용되지 않는다.
저장된 직업은 archer지만 먼저 시작된 생성 로드의 플레이어는 wizard로 남았다.
이 재현으로 자동화 순서 결함은 확인했으며, 당시 CI의 같은 상태였다고 단정하지 않는다.

검사는 이제 생성 완료와 실제 preparation/player 준비를 먼저 기다리고, fixture 저장
성공과 직업 선택 결과도 확인한다. timeout을 늘리거나 이미지/캐시 검사를 제거하지
않았다. 실패 snapshot 및 단계별 이벤트에 busy, 선택 작업, 요청/저장/플레이어 직업,
preparation 유무와 개별 준비 조건을 추가했다. 전체 프로필은 기록하지 않는다.
1초 지연 생성 대조는 실제 궁수 선택 및 warm/update 0바이트까지 확인한다.
게임 런타임·아트·SW와 운영 트래픽 예산은 변경하지 않았다. 재현 로그와 전후 상태는
`/workspace/yurika-cache-archer-fix/`에 보관한다.
